# HackAlem AI — Автоматизация формирования заказов поставщикам

## 1. Цель проекта

Разработать MVP-сервис для автоматического расчёта рекомендуемых заказов поставщикам на основе данных о продажах, остатках, товарах в пути, сезонности, росте спроса и периодах отсутствия товара.

Основной пользователь — менеджер отдела закупа.

Система не должна автоматически отправлять заказ поставщику.
Финальное решение и подтверждение заказа остаётся за ответственным сотрудником.

---

## 2. Поставщики и данные

Для MVP предоставлены данные двух поставщиков:

- IEK
- System Electric

Для каждого поставщика имеются Excel-файлы с данными о продажах, остатках, товарах в пути, сезонности и MOQ.

Основным идентификатором товара при объединении таблиц является код 1С, если соответствующее поле присутствует в конкретном файле.

Если необходимое поле отсутствует в исходных данных, нельзя придумывать его значение.

---

## 3. Must Have

Система должна:

1. Рассчитывать базовую потребность в пополнении по каждому SKU.

2. Учитывать:
   - историю продаж;
   - текущие остатки;
   - товары в пути;
   - категории товаров, если они доступны в исходных данных;
   - прогноз роста спроса.

3. Учитывать сезонность спроса.

4. Учитывать устойчивый рост или снижение спроса.

5. Выявлять периоды stockout — периоды отсутствия товара.

6. Оценивать упущенный спрос во время stockout.

7. Выявлять разовые аномально крупные продажи.

8. Не позволять разовой крупной продаже существенно искажать регулярный прогноз спроса.

9. Формировать рекомендуемое количество заказа.

10. Учитывать MOQ, если MOQ предоставлен для товара.

11. Определять поставщика.

12. Формировать краткое объяснение рекомендации.

13. Определять срочность заказа.

14. Группировать рекомендации по поставщикам.

15. Предоставлять результат в формате таблицы/дашборда.

16. Предусмотреть экспорт результата.

## 4. Data Dictionary

| Данные | Источник | Назначение |
|---|---|---|
| SKU / код товара | Код 1С | Объединение данных |
| История продаж | Динамика продаж | Регулярный спрос и поиск аномалий |
| Monthly Sales | Ежемесячные продажи | Прогнозирование |
| Остатки | Ежемесячные остатки | Остаток и определение stockout |
| Сезонность | Сезонность | Seasonal adjustment |
| Incoming | Товар в пути | Учёт уже заказанного товара |
| MOQ | MOQ | Корректировка количества заказа |
| Supplier | Источник данных | IEK / SystemElectric |

Точные названия колонок должны определяться по фактическим Excel-файлам.

Запрещено придумывать отсутствующие поля или значения.

## 5. Бизнес-логика

### 5.1 Regular Demand

Регулярный спрос — спрос на товар после обработки разовых аномальных продаж.

### 5.2 Outlier

Система должна обнаруживать аномально крупные разовые продажи.

Конкретный статистический метод должен быть выбран после анализа распределения реальных данных.

Не использовать произвольный фиксированный порог без обоснования.

### 5.3 Stockout

Нулевые или низкие продажи в период отсутствия товара нельзя автоматически трактовать как отсутствие спроса.

Система должна оценивать потенциально упущенный спрос.

### 5.4 Seasonality

Прогноз должен учитывать повторяющиеся сезонные изменения спроса и не сводиться только к среднему значению всей истории.

### 5.5 Trend

Система должна учитывать устойчивый рост или снижение спроса.

### 5.6 Forecast

Прогноз спроса должен формироваться на основе очищенной истории продаж с учётом сезонности, тренда и коррекции stockout.

### 5.7 Incoming

Товар, который уже находится в пути, должен уменьшать дополнительную потребность в закупке.

### 5.8 MOQ

Если рассчитанное количество не соответствует MOQ поставщика, итоговая рекомендация должна корректироваться согласно принятому правилу MOQ.

---

## 6. Концептуальная формула

Общая логика:

Regular Demand
→ Seasonality Adjustment
→ Trend Adjustment
→ Stockout / Lost Demand Adjustment
→ Forecast Demand

Далее:

Forecast Demand
+ Safety Requirement
- Current Stock
- Incoming Stock
= Raw Recommended Order

Далее:

Raw Recommended Order
→ MOQ Adjustment
→ Final Recommended Order

ВАЖНО:

Safety stock, конкретные коэффициенты, горизонт прогнозирования и другие параметры нельзя выдавать за требования заказчика, если они отсутствуют в предоставленном ТЗ.

Если такие параметры необходимы для MVP, они должны быть явно обозначены как:

MVP ASSUMPTION

---

## 7. Explainability

Расчёт должен быть объяснимым.

Backend должен возвращать не только итоговое количество, но и факторы, повлиявшие на него.

Пример внутреннего результата:

- forecast
- current_stock
- incoming
- stockout_adjustment
- seasonality_impact
- trend
- outliers_removed
- MOQ
- recommended_quantity
- urgency

Пользователь должен иметь возможность понять, почему система рекомендует именно такое количество.

---

## 8. Использование LLM

LLM НЕ должен самостоятельно рассчитывать количество заказа.

Все числовые значения рассчитываются алгоритмом backend.

LLM разрешается использовать только для преобразования готовых результатов расчёта в понятное человеку текстовое объяснение.

LLM запрещено:

- изменять рассчитанные числа;
- придумывать отсутствующие данные;
- самостоятельно определять количество заказа;
- заменять основной алгоритм прогнозирования.

При недоступности LLM система должна продолжать работать и формировать шаблонное объяснение без AI.

## 9. Optional

После реализации Must Have можно добавить:

- risk scoring дефицита;
- дополнительные условия поставщиков;
- визуализацию трендов по категориям;
- автоматическую подготовку сообщения/заказа поставщику.

Optional-функции не должны мешать завершению Must Have.

---

## 10. Ограничения

Нельзя:

- автоматически отправлять заказ поставщику без подтверждения сотрудника;
- использовать неанонимизированные данные клиентов;
- придумывать отсутствующие данные;
- скрывать логику расчёта за LLM.

Необходимо обеспечить:

- объяснимость;
- устойчивость к выбросам;
- обработку отсутствующих значений;
- совместимость результата с дальнейшим экспортом.

---

## 11. Приоритет разработки

Порядок реализации:

1. Загрузка данных IEK.
2. Нормализация данных.
3. Объединение данных по SKU.
4. Детекция аномальных продаж.
5. Stockout correction.
6. Seasonality.
7. Trend.
8. Forecast.
9. Current stock.
10. Incoming stock.
11. Расчёт рекомендуемого заказа.
12. MOQ.
13. Explainability.
14. Таблица/дашборд.
15. Подключение SystemElectric через тот же pipeline.
16. Export.
17. Optional-функции.

Сначала должен полностью работать IEK end-to-end.
После этого SystemElectric подключается к тому же расчётному ядру.

---

## 12. Технологическое ограничение

Основной backend проекта разрабатывается на Go.

Не добавлять другой язык программирования в основной pipeline без технической необходимости и согласования команды.

Предпочитать простую архитектуру и минимальное количество зависимостей.
